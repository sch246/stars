# 星罗 core —— 关系的编辑器

> 状态:M0(L0)。这是重构的新内核,与旧的 `src/`、`webapp/`、`media/` 并行存在,互不影响。

## 目标

星罗是**关系的编辑器与维护工具**,不是文本编辑器,也不是图可视化玩具。

- 数据是**挂在文件上的关系层**:节点指向仓库里的文件,正文留在文件里。
- **内核是本体**:库 + CLI,人和 AI 调同一套接口。UI(查看器、VS Code 插件)只是视图。
- 重点不是"建立关系",而是**让关系可维护**:查询、校验、批量变更、审阅。
- 先搓一个宇宙,让一切从里面长出来;每一步都必须能亲眼看到。

## 数据模型(内核只有这些)

- **节点**:`id`(稳定、可读)、`label`、任意 `key=value` 属性。常用属性:`type`、`summary`、`file`、`status`。
- **边**:`(from, type, to)` 三元组唯一确定,可带属性。没有边 id。
- **边类型的性质**由"模式节点"声明:`symmetric`(无向)、`acyclic`(不成环)、`single-parent`(至多一个入边)。
- **n 元关系 / 区域 / tag** 不进内核:用"中心节点 + 成员边"表达,查看器可把中心节点渲染成区域。两种表示可无损互转。
- **模式节点**:id 以 `~` 开头。`~dependsOn kind=edgeType`、`~module kind=nodeType color=#bd00ff`……
  类型本身就是宇宙里的节点,所以改类型定义不需要改代码(这是 L2 自描述的地基)。

## 文本格式

```
stars 1

node auth "认证模块" type=module file=src/auth.ts summary="登录与会话"
node session "会话" type=module
node ~related "关联" kind=edgeType symmetric=true

auth -dependsOn-> session status=proposed
auth -related- session
```

- 一行一个事实,按 id 排序,同一个宇宙总是序列化成同一段文本(git diff 友好)。
- 对称类型写成 `-t-`,方向无关。
- 文件头可带 `rev=N`:这个文件已包含操作日志的前 N 条。日志是权威的提交记录,宇宙文件可以**延迟写入**;读取时(`Store.load`)会回放文件之后的日志,所以任何进程读到的都是最新、一致的宇宙。没有 `rev` 的旧文件不做任何回放。
- 限制:`#` 注释读入时会丢弃(请用 `summary`);id 不能含空白/引号、不能以 `#` 开头。
- `file` 路径相对于**宇宙文件所在目录**(或环境变量 `STARS_ROOT`)。

## 操作与日志

所有修改走 `apply(universe, op)`,返回**逆操作**。`Store.commit` 落盘并追加一行到 `<file>.log`
(时间、`author`、操作、逆操作),所以 `undo` 免费,将来的**回放**也免费。

给 L3/L4 预留的四个钩子(现在都是空实现):
1. 写入统一入口,每个操作带 `author`(人 / AI 名字 / 将来的代码节点)。
2. 类型与规则是节点,不写死在代码里。
3. `Store.policy`:操作前的权限检查位置,现在恒为允许。
4. 安全模式:将来启动时可不加载任何代码节点。

## 视图 = 函数

画面不是数据的一部分,而是 `evaluateView(宇宙, 视图规格) -> 场景` 这个纯函数的结果(`src/view.ts`)。
规格是一组**有序规则**,第一条匹配的生效:

```jsonc
{
  "look": "galaxy",
  "select": { "withRelations": ["dependsOn"] },          // 显示哪些节点
  "size":  [{ "when": {"type":"dir"},  "attr": "size", "rollup": {"relation":"contains","op":"sum"}, "scale":"log" },
            { "when": {"type":"file"}, "attr": "size", "scale":"sqrt" },
            { "by": "degree" }],                          // 大小来自属性 / 沿关系汇总 / 度数
  "color": [{ "when": {"type":"dir"},  "by": "group", "relation": "contains", "level": 1 },   // 同一子树同色
            { "when": {"type":"file"}, "by": "attr:ext" }, { "by": "type" }],
  "style": [{ "when": {"type":"dir"}, "shape": "nebula" }, { "when": {"type":"module"}, "shape": "ringed" }],
  "relations": { "contains": { "mode": "orbit" }, "describes": { "mode": "faint" }, "*": { "mode": "line", "arrow": true } }
}
```

- **关系怎么画由视图决定**:`contains` 在 `galaxy` 里是轨道(子绕父转),在 `tree` 里是连线,在 `deps` 里被隐藏。
- **派生属性是规则**:目录大小 = 沿 `contains` 汇总子孙的 `size`;颜色可以继承祖先。
- 视图存放在宇宙里:`kind=view` 的节点,id 为 `~view/<名字>`,`spec` 属性是上面的 JSON;同名覆盖内置视图。改它,查看器立刻变化。
- CLI/AI 也能算视图:`stars views`、`stars view galaxy [--json]`。

## 容器、展开与边提升

文件夹不是特殊结构:`contains` 只是一条普通关系。任何有子节点的节点就是**容器**。
同一个容器,视图决定它以哪种身份出现 —— 关系 `R(x,y)` 的几种可视化在这里都用得上:

| 容器的身份 | 表现 | 视图 |
|---|---|---|
| **节点** | 容器本身是一个点,用连线连着它的成员(和别的节点平等地产生关系) | `tree`、`orbit` |
| **域** | 没有节点本体,只有一个包住成员的疆域;远看是一个小星系(粒子是内容的缩影),走近了是一个空间 | `galaxy`、`recent`、`arch` |
| **tag** | 没有节点本体,也不画疆域;成员身上带着它的 tag,可以点亮、参与高亮,同 tag 的成员轻轻聚拢 | `tags` |
| **中心节点** | 关系本身被"实体化"成一个节点,连着它涉及的所有元素(n 元关系) | 数据层面:给关系建一个节点即可 |

- **边提升**:容器收起时,内部的关系消失;跨容器的关系**提升**到容器上并汇总计数
  (`a/x.ts -dependsOn-> b/y.ts` ⇒ `a/ -dependsOn-> b/ ×2`)。提升的边是**派生**的(`lifted: true`),
  查看器里画成细点线并标 `×N`;面板里能看到"收起后的对外关系(含内部汇总)"。

### 空间(`layout: "spaces"`):两种进入方式,语义不同

域视图下每个容器的内部是一个**独立的空间**:自己的力学模拟,只受自己内部关系的约束,和外界没有引力往来
(所以不会出现"整棵树被拽成单向放射状"的样子)。从外面看,一个空间就是一个点/小星系。进入它有两种方式:

| 操作 | 含义 | 发生了什么 |
|---|---|---|
| **放大**(到容器几乎占据小半屏幕,`space.enterAt`,默认 0.42 × 屏幕短边)/ `⏎` / 面包屑 | **切换空间**,和切换路径一样 | 有来源和目的,所以画面是连续的:镜头从外层"钻进"容器,之后画面里只剩这个空间;缩小或 `⌫` 回到上一层 |
| **双击** / `E` | **显式地把不同层级放到一起** | 容器在原地展开成一个域,里面是它自己的空间(仍然独立模拟),外层的东西不动;再按一次收起,`0` 全部收起 |

- **视觉是一个区间,切换是一个临界点**。画面只由 ρ 决定 —— 容器在屏幕上的盘半径(在子空间里时,用子空间的范围按同一几何折算),
  以进入阈值 T 为单位。切换只在 ρ ≥ T(进入)和 ρ < 0.95T(退出)时发生 —— 只留 5% 防抖,放大一点进去、缩小一点就出来
  (滚轮约 2 格;以前退出要缩到 0.54T,得滚 6 格)。因为两边按同一个 ρ 画,切换前后是同一幅画面
  (实测滚轮逐级穿过切换点:切换那一步的画面变化和相邻两步一样大,没有跳变)。
- **小星系展开成里面的空间**(ρ 从 0.4T 到 T):收起的容器画成小星系,旋臂上的每颗粒子本来就对应一个后代(内核给缩影带上了 id)。
  放大时粒子从旋臂上的位置一路移到它对应节点的真实位置、由小点长成那颗节点(粒子渐隐、节点在同一处渐显),
  孙辈的粒子汇入它所在的子星系,星系核心的光晕渐隐,连线晚一点出现,标签展开过半才出现。所以全程每个东西只出现一次 ——
  以前是"星系的粒子"和"半透明的真实节点"叠在同一块地方,分不清谁是谁。ρ 从 0.6T 到 2.2T,外面的兄弟渐渐淡到 15%,4T 以后完全消失。
- 显式的进入/退出(⏎、按钮、⌫)是一次缩放动画,同样走这个连续的过渡。刚退出来时,那个容器会继续按 ρ 收拢回星系,
  即使指针已经不在它上面。
- 自动展开(旧版的"语义缩放")已经去掉:展开会让不同层级挤到一起,这只应该是用户主动的决定。
- 跨空间的关系:在空间里看不到外面的节点,但能看到"从这里通往外面"的关系 —— 屏幕边缘的**外部连线桩**,
  按(成员、关系类型、方向、外面的落点)汇总计数;面板里列出"通往空间外的关系"。
- **节点预算**(平面布局,`expand.maxNodes`,没写 `depth` 时默认 1500):一层一层往下展开,同一层先展开孩子少的,
  再展开就超出预算的保持收起(一个小星系)。上万个文件的仓库在 `orbit`/`tree` 里因此不会"爆炸"成一张没法看的图
  (实测 1.7 万节点:画面 1500 个节点、每帧 ~9ms,原来全部展开时每帧 ~100ms、布局半径 2 万多)。
  双击/`E` 手动展开不受预算约束;不在画面里的容器(比如 `tags` 视图隐藏的目录)是透明的,不会因为预算把内容藏起来。
  CLI:`stars view orbit --max-nodes 3000`。
- 容器大小沿 `contains` 汇总,所以展开/收起前后节点大小不变;归一化对全部入选节点统一做,不会跳变。
- `contains` 里有环时会在环上断开一条父链,保证每个节点都可达。

CLI:`stars view arch`(架构级,只展开一层、隐藏文件)、`stars view galaxy --depth 2`、`--expand a/,b/`。

### 内置视图
`galaxy`(默认,空间:放大切换、双击就地展开)· `recent`(空间,颜色 = 多久之前动过)· `tags`(文件夹作为 tag,不显示目录本体)·
`orbit`(全部展开,子绕父转)· `arch`(空间,只看目录与模块)· `deps`(只看语义关系)· `tree`(平面连线)

`tags` 视图的规格:`"tags": { "relation": "contains", "depth": 2 }` —— 每个节点带上它最近 2 层祖先作为 tag,
`select.hideTypes: ["dir"]` 让目录本体不出现。底部的 tag 栏可以点亮多个 tag,命中的节点高亮。
布局是按 tag 层级的**圆堆积**(`d3.pack`):顶层 tag 一团,团里按第二层再分小团,每个节点被拉向自己的锚点,
团上写着 tag 名(第二层的名字在团够大时才出现)。只把节点拉向"组心"是不够的 —— 初始位置随机时所有组心都在中间,
各组永远分不开(1.5 万个文件会变成一个均匀的圆盘)。

背景(远方的星系 / 只有星点 / 纯黑)用 `✦ 背景` 按钮或 `B` 切换,记在浏览器里。

### 同一份代码在两端运行
`model.ts` / `expr.ts` / `view.ts` 只依赖标准库。`stars serve` 把它们去掉类型后以 JS 提供给浏览器(`/core/*.js`,
用 Node 的 `module.stripTypeScriptTypes`,这是实验性 API),所以展开、收起、切换视图完全在浏览器本地计算,
CLI 与查看器永远是同一套逻辑。

## 信号与"最近编辑"

宇宙文件本身不记录时间,但有两个来源,做成视图可引用的**信号**(`EvalOptions.signals`,id → 毫秒时间戳):

| 信号 | 来源 | 含义 |
|---|---|---|
| `touched` | 操作日志 | 这个节点(或连着它的边)最近一次被编辑 |
| `fileChanged` | git 最近提交时间;工作区里未提交的文件用 mtime | 节点指向的文件最近一次变动;目录取后代里最新的 |

(干净克隆下所有文件的 mtime 都是克隆时间,没有意义,所以 mtime 只用于"工作区里有未提交修改"的文件。)

视图规则里:`{"by":"recency","signal":"fileChanged","halfLifeDays":10,"from":"#2f3b6e","to":"#ffcf70"}`
让颜色随"多久之前动过"在冷→热之间渐变(每过一个半衰期,新鲜度减半);`size` 规则也可以用
`signal` + `recency`;`rollup: {relation:"contains", op:"max"}` 让容器取后代里最新的。内置视图 `recent` 就是这样的热力图:
大小是体量,颜色是新旧。视图仍是纯函数 —— 当前时间(`now`)和信号都是输入,所以测试里可以固定它们。

## 视图规则编辑器与接口

规格就是宇宙里一个 `kind=view` 的节点,所以**所有入口走同一条通道**(都带 `author`、写操作日志、可撤销):

- 查看器里的 **✎ 视图规则**:改 JSON,250ms 后实时预览(无效时给出具体问题),"保存到宇宙"/"另存"/"删除"。
- CLI:`stars view <名> --spec` 读,`stars view-set <名> --spec '<JSON>' | --from 文件` 写(先 `validateSpec`)。
- HTTP:`POST /api/op`(`{op, author}`),`GET /api/history`、`/api/state?commit=`。
- 直接改 `universe.stars`:`~view/<名>` 节点的 `spec` 属性。

**写接口的安全**:默认只监听 `127.0.0.1`;校验 `Host`(防 DNS 重绑定);写和读历史都要求页面里内嵌的
随机 token(每次启动不同),并拒绝跨源请求。`--host 0.0.0.0` 会警告。

### 自由度的阶梯(性能优先,不加沙箱)

| 层级 | 形式 | 状态 |
|---|---|---|
| a. 规则 JSON | 有序规则 + `when` 相等匹配 | ✅ |
| b. 表达式 | 规则字段里写 JS 表达式:`size[].expr`、`color[].expr`、`style[].expr`、`when`、`select.where` | ✅ 直接编译成原生函数 |
| d. 槽位接代码节点 | 表达式里 `fn.名字(...)` 调用宇宙里 `~fn/名字`(`kind=function`,`code` 是一个函数表达式);`stars fn-set` 创建,agent 可以随手生成/替换 | ✅ 进程内直接调用 |
| c. 自定义布局力 | 视图规格 `forces: ["~fn/名字"]`,函数节点每 tick 被调用 `(nodes, links, alpha, ctx)` | ✅ |
| d. 整体替换成函数 | `(node, ctx) => scene` 一个函数管一整个视图 | 未做 |

设计取舍:**视图是"第一遍搜寻"的工具,所以必须快,不能为了安全多绕一层。** 因此表达式和函数节点都被
`new Function` 编译成原生 JS,每条只编译一次,运行时按节点下标读列(类型化数组),不为每个节点建对象、不经过解释器、
不跨进程/Worker 来回序列化。10 万节点上,四条表达式(筛选 + 大小 + 颜色 + 样式)的编译约 0.5 秒,展开/收起仍是 ~12ms。
安全上**没有沙箱**:表达式与函数节点以页面/进程的全部权限运行。个人使用时这是对的取舍;如果以后要共享/导入别人的宇宙,
再加一个"默认不执行函数节点"的开关即可(函数节点本来就是显式的、可以被识别的节点)。
JSON 仍是规范形式:界面编辑它,AI 补丁它,CLI 校验它(`validateSpec` 会检查表达式语法与 `fn.x` 是否存在)。

#### 表达式里可用的东西
- 变量:`id label type degree depth children descendants`;任意属性名(全是数字的属性自动是数值列,如 `size`、`ext` 是字符串列);信号 `touched fileChanged`(毫秒时间戳,没有记录 = 0)。
- 函数:`log log1p log2 sqrt pow min max abs floor ceil round clamp(x,lo,hi) mix(#a,#b,t) hsl(h,s,l) hash(str) days(t) recent(t,半衰期天数) now`,以及 `fn.名字(...)`。
- 颜色表达式返回 `"#rrggbb"`,或 0..1 的数(配合规则里的 `from`/`to` 渐变);样式表达式返回形状名。

```bash
stars fn-set heat --code '(t, s) => log1p(s) * (days(t) < 7 ? 3 : 1)'
stars view-set hot --spec '{"select":{"where":"type == \"file\""},
  "size":[{"expr":"fn.heat(fileChanged, size)","range":[2,14]}],
  "color":[{"expr":"recent(fileChanged, 3)"}]}'
```

## 性能

视图是"第一遍搜寻",所以展开/收起必须是毫秒级。`evaluateView` 被拆成两步:

- `compileView(宇宙, 规格, 信号)`:算好**所有**节点的静态外观(大小、颜色、样式、汇总、深度、度数……)。内部用整数下标 +
  类型化数组 + CSR 邻接表,规则前提预编译,颜色查找记忆化。宇宙/规格/信号变了才重新编译。
- `fold(展开状态)`:只算"现在显示哪些"和边提升,是数组上的线性扫描,不碰任何节点的外观。

`node bench/view.bench.ts 100000`(10 万个文件、约 20 万条边)的实测:

| | 之前 | 现在 |
|---|---|---|
| 展开/收起一个目录 | ~2500 ms | **~16–22 ms** |
| 编译(仅数据变化时) | — | 0.3–0.6 s |
| 含 4 条表达式的视图,编译 / 折叠 | — | ~0.5 s / ~12 ms |

(测试环境:4 核云容器,Node 22。)度数现在是全图的静态值,所以展开/收起时节点大小不会跳变。

渲染侧的手段(查看器):发光用预渲染精灵图而非每帧建渐变;视口外不画;屏幕上小到看不清的节点降级成点,收起的星系
小于阈值不画粒子;边、星系粒子、背景星点按样式/颜色合批;域的凸包缓存并节流;标签规划节流。每帧 `fill` 调用从约 2.8 万降到几十次。
**诚实的说明**:开发环境只有软件渲染,测不出真实帧率,所以我只报了调用次数,没报 FPS;真机有 GPU 时应当明显更好,但没有实测。

## 审阅:接受/拒绝提议,把汇总边提升为真边

AI 用 `--proposed` 写入的边是"待确认"的。查看器里:

- **✓ 审阅**(带数量徽标,没有待确认的提议时按钮变淡):列出所有待确认的边、**是谁在何时提议的**(从操作日志回溯),逐条 ✓ 接受 / ✗ 拒绝(删除),
  或"全部接受/全部拒绝",还有"↶ 撤销上一步"。点一行跳到该节点。
- 节点详情里的待确认边旁边也有 ✓ ✗。
- 收起的容器的"对外关系(含内部汇总)"里,每条汇总出来的边有"提升"按钮:在两个容器之间写一条**真实存在**的边
  (带一条说明由多少条内部关系汇总而来)。这是"从统计走向断言"的一步 —— 汇总是派生的,提升后才成为宇宙里的事实。

所有写入都走同一条通道(带 `author: viewer`,写日志,可撤销)。

## 宇宙参数与热量(⚙ 参数)

物理参数可以在查看器里实时调,存在浏览器里(所有项目共用),`恢复默认`一键回去:

| 参数 | 作用 |
|---|---|
| 保持热量(默认开)/ 热量 | 模拟始终保持一点温度(`alphaTarget`,默认 0.03),和拖动时一样是"活的":对变化立刻有反应,但温度低,不抖。关掉则静止后停算,省电 |
| 公转 | 保持热量时,空间里的成员绕空间中心缓慢公转(视图里 `contains` 的 `spin` 再乘这个倍率;galaxy 默认约每秒 3px)|
| 斥力 / 连线长度 / 引力 / 间隙 / 阻尼 | 力导向的各项倍率与常数,平面布局和空间布局都生效 |
| 进入空间 | 放大到容器占屏幕短边的多少比例时进入它;0 = 跟随视图(默认 0.42)|
| 淡入淡出(默认开) | 空间内外切换时的交叉淡入淡出;关掉则瞬间切换,没有任何过渡 |
| 真实体积(默认开) | 目录和文件用同一套体积公式(同 scale/区间;目录仍按 contains 汇总子孙字节数);就地展开不撑大占用,内容等比缩小,要看清就滚轮放大 |
| 体积映射(默认 sqrt) | 真实体积开启时,字节数 → 半径 的缩放:sqrt(面积 ∝ 体积)/ log(更紧凑)/ linear |
| 体积下限 / 体积上限 | 真实体积映射后的半径区间(默认 2–16) |
| 边界(默认开) | 文件夹的虚线边界与半透明底;关掉后只剩文字与交互,边界和底色全透明(视图区 "▢ 边界",或视图规则 space.boundary=false) |

**体量 → 半径的映射**(视图的 size 规则,[view.ts:208-210](src/view.ts)):默认目录 = 沿 contains 汇总子孙字节数后取 log(区间 5–17),文件 = 字节数取 sqrt(区间 1.8–9);scaleValue 见 [view.ts:355](src/view.ts)。
开启"真实体积"后,目录和文件改用**同一套**公式(同一个 scale 与区间 [2,16];目录仍汇总子孙字节数),同样字节数的文件和目录半径相同。
画出来的"盘面积 ∝ 半径²":sqrt 时面积 ∝ 字节数;log 时面积 ∝ (log 字节数)²,巨大的内容被强烈压缩。收起容器的盘半径 D = 半径 × BODY(4.2),斥力按 D 线性给。

**按下、拖动都不改变温度与动力学**。斥力、引力、连线随温度缩放,而碰撞不随温度缩放 —— 温度一变平衡点就变,
以前表现为按住节点时整张图收缩、松开又胀回去,刚切换视图时(温度高)紧凑、冷下来以后几十秒里慢慢胀开。现在:
- 按下什么都不做;指针挪动超过 3px 才算拖动。
- 拖动只是**施加一个力**:被拖的节点被一根弹簧拉向指针(不钉住它),周围的节点通过平常的力去响应。
- 域之间的推力、公转、拖动的拉力都按温度缩放(以平时的热量为 1,封顶 8 倍),平衡点与温度无关。
- 唯一的例外:热量关着时模拟是停的,力推不动任何东西,这时拖动临时升到热量设定值,松手后冷却。

实测:按住 3 秒,温度不变,平均半径变化 ≤0.7%(以前 orbit / tree 是 −8% / −12%);拖动时温度全程不变,
节点停在离指针 2~10px 处(邻居把它往回拉的那一点);切换视图后几秒内就稳定。

只有这一帧画到的空间(当前空间 + 就地展开的)保持热量,看不见的空间冷却后停算。就地展开的子空间一直在动时,
只有当它的疆域半径变化超过 2px 才通知父空间让位 —— 否则父空间会被不停地重新加热、抖个不停。
实测(热量开):每帧位移 ~0.045px,帧间速度变化 ~0.0001px(不抖);关掉 4 秒后完全静止。

## 在查看器里看和改文件(侧栏就是编辑器)

像原版星罗:**点一下文件节点,侧栏上半是它的属性,下半就是它的内容**,不需要 VS Code(将来在 VS Code 插件里,同样的动作会打开它自己的编辑器)。

- **轻**:点一下就打开,所以只要开头 24 KB(`/api/file?head=`,切在最后一个换行处),此时是只读预览;
  点进编辑框或滚到底才载入全文、变成可编辑(保留光标与滚动位置)。超过 2 MB 的文本只预览开头,不可编辑;图片直接预览。
- **点别处就收起**:点空白处或别的节点,侧栏回到别的内容;有未保存的修改会**自动保存**。保存被拒(文件在你打开之后被别处改过)
  就把你的修改留着,底部提示"回去处理",回去后能选"载入磁盘版本"或"用我的覆盖"。也可以随时 `Ctrl/⌘+S`。
- **实时**:磁盘上的文件变了(实时同步的信号立刻触发,否则每 3 秒查一次修改时间):没改过就直接载入新版本,改过就提示冲突。
  保存时带上打开时的修改时间,别处改过会被拒绝(409),不会悄悄覆盖。原来是 CRLF 的文件保存后仍是 CRLF;宇宙自己的存储与 `.git` 只读。
- **宽度**:拖侧栏左边缘调整,看文件时和平时各记各的,双击边缘恢复默认。
- `VS Code ↗` 是 `vscode://file/…` 链接,查看器和文件在同一台机器上时可用。
- 接口:`GET /api/file?path=`(`&head=N` 只要开头、`&stat=1` 只要大小与修改时间)、`POST /api/file {path, content, mtime}`、
  `GET /api/raw?path=&t=<token>`(图片;`<img>` 带不了请求头,所以 token 放在查询参数里)。路径限制在项目目录内。

浮动面板(项目、参数、审阅)点面板外面就关,平移和缩放不算;视图规则编辑器只在没有未保存的草稿时才这样关;时间线是一种模式,不受影响。

## 项目:一个文件夹一个宇宙,一个服务打开多个

`stars serve` 启动时监听一个宇宙(主项目),之后在查看器里按 `P`(或点左上角的项目名)打开**项目面板**:

- **已打开**:这个服务里正在开着的项目,点击切换。切换只是换一条事件流,其它项目的实时同步继续在后台跑。
- **最近**:打开过的目录(记在 `~/.config/stars/recent.json`,遵守 `XDG_CONFIG_HOME`),★ 表示里面有宇宙。
- **浏览文件夹**:服务端的目录树(在没显示器的机器上用反代访问时,浏览的是那台机器的磁盘)。
  有宇宙的目录点"打开";没有的,"在这里建立宇宙"会用创世文件建一个,并扫描这个目录(遵守 `.gitignore`)。

项目 id 是宇宙文件绝对路径的哈希(稳定),写在地址栏 `#view=…&p=…` 里,所以每个浏览器标签可以停在不同的项目上,
刷新不丢;服务重启后,带着 `#p=` 刷新会按浏览器记住的目录自动重新打开。接口上就是给所有请求加 `?p=<id>`
(`/events`、`/api/op`、`/api/undo`、`/api/history`、`/api/state`),加上 `GET /api/projects`、`GET /api/ls?dir=`、
`POST /api/open {dir, create}`。`serve --watch` 时每个打开的项目都会开自己的文件系统同步。

## 在没有显示器的机器上使用

查看器是一个网页,服务跑在哪台机器都行。你的情况(Ubuntu 没有显示器、Windows 有),四种办法,按推荐度:

1. **SSH 隧道**(最简单,默认的安全设置不用动):在 Windows 上
   `ssh -L 4321:127.0.0.1:4321 你@ubuntu地址`,然后浏览器开 `http://localhost:4321`。Ubuntu 上正常运行 `node core/src/cli.ts serve`。
2. **反向代理**:`stars serve --allow-host stars.你的域名.com`(或环境变量 `STARS_ALLOW_HOSTS`,逗号分隔)告诉服务"这个域名是自己人"。
   nginx 要关掉对事件流的缓冲(服务已发 `X-Accel-Buffering: no` 并每 20 秒发一次保活):
   ```nginx
   location / {
     proxy_pass http://127.0.0.1:4321;
     proxy_http_version 1.1;
     proxy_set_header Host $host;
     proxy_buffering off;
     proxy_read_timeout 1h;
   }
   ```
   (`--host 0.0.0.0` 会监听所有网卡,局域网里的人都能访问,启动时会警告;写接口仍受 token 保护。)
3. **静态导出**:`stars export universe.html` 生成一个自包含的 HTML(查看器 + d3 + 视图内核 + 当前宇宙,约几百 KB,
   **零网络请求**),`scp` 到 Windows 双击打开。只读:能切视图、缩放展开、搜索、在编辑器里预览规则,但不能保存、没有时间线与审阅。
4. **在 Windows 上直接跑**:装 Node ≥ 22.18,`git clone` 同一个仓库,`node core/src/cli.ts serve`。宇宙文件在 git 里,
   分支、时间线、按事实合并都照常工作(`bash` 演示脚本需要 Git Bash/WSL)。

## 实时同步:文件系统 → 宇宙

`stars serve --watch`(或单独的 `stars watch`)让宇宙里的 `dir`/`file` 节点随磁盘实时变化,像 VS Code 的资源管理器。

**设计原则:事件只是线索,真相是重新读目录。** 监听器只负责告诉我们"哪些目录可能变了",`fssync.ts` 对这些目录
重新 `readdir`,与宇宙对账,算出一批操作。所以不依赖各平台事件语义的差异(创建/删除/改名/覆盖写),事件丢了、重复了、
乱序了,下次对账都会自愈。忽略规则不自己实现,直接问 `git check-ignore`,和 `.gitignore` 语义分毫不差。

据我所知 VS Code 的做法与此同源(原生递归监听、排除目录、事件合并与节流、风暴时放弃逐条而整体刷新、网络盘退化为轮询);
我们用零依赖的 Node 做了同样的取舍:

| | Windows / macOS | Linux |
|---|---|---|
| 监听 | 系统原生递归监听(一个句柄管整棵树) | 每个**宇宙里已知的、没被忽略的**目录一个 inotify 监听(不碰 node_modules) |
| 限制 | 几乎没有 | 达到 `fs.inotify.max_user_watches` 时降级为 10 秒一次的定时对账,不崩 |

事件处理:攒 80ms(最长 500ms)去重 → 一批脏目录 → 对账 → **一次提交**;脏目录超过 300 个(切分支、`npm install`)就做一次全量对账;
每 120 秒全量对账一次兜底;`.git/HEAD`/`index` 变了(提交、切分支)就刷新 git 派生的信号 —— 不用在仓库里装钩子。
新建目录时监听器是后加的,会补读一次堵住竞态。
宇宙自己的存储(宇宙文件本身、`*.stars.log`、原子写的 `.tmp`、签名 `.sig`)不是居民:扫描和同步都跳过它们,
它们的写入也不会触发对账(否则每次提交都会改变"宇宙文件"节点的大小,自己喂自己)。别的 `.stars` 文件照常收录。

**对用户数据的态度**(文件被删 ≠ 关系应该消失):

| 磁盘上发生了 | 宇宙里 |
|---|---|
| 新建文件/目录(含整棵子树) | 新增节点 + `contains` 边,属性与 `scan` 一致 |
| 删除,节点只有 `contains` 边 | 移除节点 |
| 删除,节点带语义关系(依赖/描述/AI 提议…) | **保留**并标记 `missing=true`(lint 警告),文件回来自动取消 |
| 改名/移动(同名同大小;或同扩展名同大小;目录则看内容签名) | `renameNodes`:节点连同**所有关系**一起改名,归属目录跟着变;**有歧义就不猜**,当作一删一增 |
| 修改内容 | **不写宇宙**(否则 git diff 全是噪音)。大小与修改时间作为"实时信号"推给查看器,覆盖同名属性(`size`),所以节点大小立刻变化 |

### 增量传输
查看器连上后收一份完整快照,之后服务端只推:`ops`(新追加的日志条目,浏览器用同一份 `apply()` 在本地更新宇宙)、
`signals`(实时的大小/修改时间)、`issues`(节流 1.5s)。日志序号有缺口、`apply` 失败,浏览器会自己重连要一份新快照。
宇宙文件被外部改动(`git checkout`、手改)而日志没动时才推完整快照;Store 自己的延迟落盘靠一个旁路签名文件识别
(放在 `.git/` 里,不会被提交或参与合并),所以不会误判成外部修改。编译很贵时(大宇宙)查看器按上一次编译耗时自适应地合并更新。

### 实测(4 核云容器,Node 22)
| | 结果 |
|---|---|
| 浏览器端到端:新建文件 → 出现节点 | ~170 ms |
| 改名(关系保留) | ~170 ms |
| 修改内容 → 节点大小变化 | ~360 ms(宇宙文件无新增写入) |
| 2000 个文件一次落地 → 全部出现 | ~450 ms,只提交 2 次 |
| 3 万文件的宇宙:启动全量对账 | ~0.5 s |
| 3 万文件:新建 1 个文件(落进宇宙) | **73 ms**(优化前 1746 ms:每次同步重新解析 3.6 MB 并整份重写) |
| 空闲 | 0 CPU,内存 ~114 MB,监听数 = 目录数 |

`node bench/watch.bench.ts 30000` 可复现。演示:`AUTO=1 bash demo/live-fs.sh`。

## 历史、分叉与合并

回放的依据是 **git 里宇宙文件的提交图(DAG)**,不是一条线:`gitHistory` 取所有分支上改动过它的提交
(含合并提交的两个父节点)和分支名,`gitSnapshot` 还原任一提交时的宇宙,`diffUniverses` 给出与父提交的差异。
操作日志(`.log`)是线性的,只负责提交**之内**的细粒度(谁、何时、改了什么,以及撤销);它是只追加的,
所以 `*.stars.log merge=union`。

宇宙文件是排序后"一行一个事实",两个分支在同一处相邻插入时 git 的**文本**合并会冲突。所以提供了**按事实的三方合并**
(`merge.ts`):节点/边按身份合并,同一事实的**不同字段**各改各的能自动合并;只有"同一字段改成不同值"、
"一边删一边改"才算冲突(取 ours 并报告),"一边删节点、另一边给它连了边"会恢复节点。
`stars install-merge` 把它装成 git 合并驱动,并在 `.gitattributes` 里写上 `*.stars merge=stars` 与 `*.stars.log merge=union`
(之前漏了后一行:两个分支都改过宇宙时,合并必然在操作日志上冲突)。

查看器的 **⏱ 时间线**:画出分支与合并,点击任一提交回放那一刻的宇宙(新增节点有绿环 + 扩散动画,修改的是橙环,
顶部显示 +新增 ~修改 −删除),◀ ▶ / ← → 单步,▶ 沿主线播放,Esc 回到现在;有未提交修改时会多一个"工作区"。
回放时节点位置按 id 延续,所以能看到宇宙"长"出来。演示:`bash demo/history.sh`(生成一个有分叉与合并的仓库)。

**文件夹的历史**:宇宙文件是新建的(还没提交过)时,它自己没有历史,但仓库本身的历史可能很长。这时时间线自动改看所在文件夹的
git 历史(头部的按钮可以在"宇宙文件的历史"和"文件夹的历史"之间切换):提交图是文件夹自己的;某个提交时的宇宙由那时的文件树
现场长出来(`git ls-tree`,和 scan 同样的规则,宇宙自己的存储不算),再挂上现在的模式、视图、概念和两端都还在的语义关系。
单步回放时上一个提交的结果有缓存。

长而复杂的历史:
- 取的是本地分支、远程分支、标签与 HEAD 上**改动过宇宙文件**的提交,`--full-history --simplify-merges`
  保留真实的分叉与合并、去掉没动过它的合并;`--date-order` 让横轴是时间(并行的分支交错排在各自的泳道上)。
- 先载入最近 300 个,`更早 …` 每次翻倍往前载入(`/api/history?limit=`)。差异按提交的**真实第一父提交**算,不依赖窗口。
- 泳道布局:每条边沿自己的泳道走,只在分出、汇入时拐一下弯;泳道用完就回收。不会再有横跨整张图的斜线。
  顶部是日期刻度,分支名标在它最近一次动过宇宙文件的提交上(指向的提交没动过时往前找)。面板最多占 34% 屏高,超出滚动。
- 实测(合成仓库:517 个提交、52 个分支、67 个合并):打开 ~0.9 s,13 条泳道,横穿的斜线 0 条。

## 校验(lint)

`stars lint`,有 error 时退出码 1。规则在 `src/lint.ts` 的 `RULES` 里,一项一个函数:

| 规则 | 级别 | 说明 |
|---|---|---|
| `dangling-edge` | error | 边指向不存在的节点 |
| `cycle` | error | `acyclic=true` 的类型出现环 |
| `multiple-parents` | error | `single-parent=true` 的类型有多个上级 |
| `undeclared-edge-type` / `undeclared-node-type` | warn | 类型没有对应的模式节点 |
| `missing-file` | warn | `file` 指向的文件不存在 |
| `orphan` | info | 没有任何关系的节点 |
| `proposed` | info | 等待人确认的 AI 提议边 |

AI 建议用 `stars link ... --proposed --author <名字>` 写入;人用 `stars accept` 确认。

| 级别 | 内容 | 状态 |

## 已知限制 / 待决问题

- 多进程并发写入是"最后写入者胜"(每次 commit 前会重新读盘,窗口很小,但没有锁)。
- `contains` 同时用于文件系统层级(`single-parent`)和逻辑分组时会冲突:逻辑上的"模块包含文件"目前只能用 `describes`。是否拆成两种类型(`contains` / `groups`)待定。
- 查看器是独立的小实现,**没有**复用旧 webapp 的渲染层(它绑定在旧 schema 上)。`rollup` 假定关系无环。
- 展开/收起状态、所在的空间不持久化(刷新后回到顶层)。
- 项目面板还不能"关闭"一个已打开的项目(重启服务即可);浏览文件夹在 Windows 上换盘符要手输路径(如 `D:\`)。
- 回放以提交为粒度;提交之内的细粒度(操作日志)还没接进时间线。回放时看不到被删除的节点(只显示 −N)。
- 表达式/函数节点没有沙箱(有意为之,见"自由度的阶梯");自定义布局力(c 级)已支持(forces),整体替换视图的函数(d 级)尚未实现。
- 每次数据变化都会重新编译视图:10 万节点约 0.3–0.6 秒,更大规模需要增量编译(查看器已按耗时自适应合并更新)。
- 实时同步:`stars watch` 与 `stars serve`(不带 `--watch`)分属两个进程时,服务端每次文件变化要重新解析宇宙文件(3 万文件约 0.5 s),建议用 `serve --watch` 合并成一个进程;重命名识别只在同一批事件里配对,跨很长时间的"先删后建"会被当作删除+新增;日志在大批量落地时会变大(存了逆操作,2000 个文件约 0.6 MB)。
- 背景里的远方星系纯属装饰(固定种子,不可交互,`B` 可关);让它们代表真实的"别的宇宙"(= 别的已打开项目)是后话。
- Windows/macOS 的原生递归监听在本环境(Linux 容器)里没有实测过。
- `/core/*.js` 依赖 Node 的实验性 `stripTypeScriptTypes`,将来 API 变了需要换成构建步骤。
- 还没有查询语言;`ls/nb/path` 只覆盖最基本的过滤、邻域、最短路径。
